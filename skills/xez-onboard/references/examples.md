# Worked examples

These examples distinguish onboarding files from the first ordinary task they prepare. They grant no publication, spending, submission or merge authority.

## Software — repair a calculation

**Input:** A checkout with a rounding defect, a manifest/lockfile, CI that names an existing focused test command, and custom agent guidance requiring regression coverage. The person wants independent operation and no delivery pipeline.

**Onboarding:** Read the manifest and CI without executing them; record the exact check command and working directory as detected. Reuse the existing guidance, preserve its regression rule, omit MCP and pipeline config, and preview only a missing `.local/` ignore rule or a useful guidance clarification. Ask about the integration branch only if Git evidence and the request leave it ambiguous. Verify the selected setup edits; do not claim to have repaired application code during onboarding.

**First ordinary task:** “Repair the supplied calculation case, add a regression that fails for it before the fix, and run the existing relevant tests.” Deliver the patch and actual test results locally. Missing dependencies mean those tests are pending, not passed. A draft/commit/PR requires that task's authority; no example authorizes merging or publishing.

## Agency — draft a campaign brief

**Input:** A non-Git folder with an audience note, a budget spreadsheet, supplied claims evidence and a request for a campaign brief. No scripts or QA pipeline exist; the person coordinates tasks independently.

**Onboarding:** Identify campaign/marketing work and a Markdown brief as the intended output. Preview one concise agent guidance file linking the supplied materials and naming the existing output folder, plus `.local/` ignore protection when needed. No branch, tracker, software tests, pipeline, MCP or invented budget approval is required. Verify links and the guidance's preservation of audience/budget/claims constraints.

**First ordinary task:** Draft the brief and check audience fit, totals against the supplied budget and every factual claim against supplied evidence. Deliver the draft and a short evidence table with unsupported claims flagged. Do not buy media, contact clients or publish the campaign. Missing source material remains an explicit gap.

## Research — revise a paper section

**Input:** A paper section, bibliography, provided source excerpts and a methods note. There may be Git, but no GitHub or test suite. The user selects leader operation with an already supported project client.

**Onboarding:** Record research as the domain and a revised section with citation notes as the output. Preserve the project's citation/style rules, preview one guidance update and only the chosen client's project MCP snippet. Report files prepared; trust, login, integration and attachment remain numbered user actions. Do not turn Git presence into a software delivery pipeline.

**First ordinary task:** Revise the section, trace citations to the provided sources, check method descriptions and state limitations without inventing results. Deliver a local revised section and unresolved-source list. Unavailable full texts are not verified citations. No journal submission, public preprint upload or claim of scientific acceptance follows from a completed draft.
