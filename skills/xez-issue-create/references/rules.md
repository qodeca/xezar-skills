# Communication

Lead with the outcome and next action. Link the resulting issue or draft; keep search scope, authority, and recovery details in the receipt. Do not repeat the entire issue body after creation. Use the skill name in backticks when naming it. No attribution or automatic agent mentions, no issue comments, and no pipeline claims are part of this create-only operation.

- **Gate reporting: collect everything, then report once.** Evaluate every gate before
  reporting any of them, and name all the failing ones together. Reporting the first
  failure and stopping teaches the reader to fix one thing, re-run, and discover the next
  — a full cycle per problem, when one report could have listed them all. A gate's result
  is one of five words: `pass`, `findings`, `unknown`, `not-applicable`,
  `evidence-unavailable`. Only `pass` and `not-applicable` are satisfied.
  **`unknown` is never a pass** — it says the check did not happen, which is not the same
  as the change being fine, and it is not a failure of the change either.
  `evidence-unavailable` does not pass: if the source could not be reached, nothing was
  verified, and exempting it would let anyone through by making the source unreachable.
  Say which gate produced which word, and never report a status you did not derive from
  an input you actually had.

- **Every finding gets a disposition, and silence is not one of them.** A review finding
  stays open until it carries exactly one of three: **fixed in `<sha>`** (name the commit —
  "fixed" with no sha is a claim the reader has to go looking for), **disputed, with
  evidence** (why it is wrong and what the reviewer can read to check — a file and line, a
  test run, a spec clause; "I disagree" is not a disposition), or **deferred, naming the
  issue** (a tracker issue that exists, by number — deferring without filing is dropping,
  with extra words). A reply that addresses four of six findings has not addressed six.
- **Degrade to a stated behaviour, never to a silent one.** When something a step needs is
  unavailable — a tool that is not installed, an API that errors, a file that is not there —
  say what you did instead and what it cost. An unavailable dependency is never treated as
  a satisfied one: that is the same defect as reading a label that was never created as a
  check that passed.
- **Absent is not `false`.** Reading a config value, an environment variable or an API
  field, keep "set to off", "not set" and "could not be read" apart. Collapsing them is how
  a gate turns into a no-op — `jq`'s `//` operator treats `false` as empty, so `.flag //
  true` silently turns an explicit `false` into `true`. And state the scope of an absence
  claim: "I did not find X in the files I read", never "X does not exist".
