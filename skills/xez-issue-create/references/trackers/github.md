# GitHub operation mapping

Use `gh` already available in the project environment. Commands below describe argument vectors, not shell strings to interpolate. Invoke through an argument-array process API with shell execution disabled; if only a shell is available, use properly quoted data variables populated through a data file, never eval or interpolation of issue text into shell source. Validate a resolved repository as OWNER/REPO (each segment letters, digits, underscores, dots, hyphens; neither empty, `.` nor `..`); retain a separately validated trusted host for enterprise. Issue numbers are positive decimal integers. Confirm the destination through a read before any mutation.

## Read operations

- **search-issues**: `gh issue list --repo OWNER/REPO --state all --search QUERY --limit 100 --json number,title,state,url,body,labels`. Pass QUERY as one value, derived from distinct symptom/outcome phrases; inspect related references separately. Record each actual query and count. A full limit is potentially truncated: narrow or page supported reads until the search scope is complete, otherwise stop publication. Check exit status and parse the response as an array of issue records, not merely valid JSON.
- **get-issue**: `gh issue view NUMBER --repo OWNER/REPO --json number,title,body,state,url,labels`. Inspect likely matches regardless of their state.
- Existing labels: `gh label list --repo OWNER/REPO --limit 1000 --json name`. Treat a capped/unavailable list as incomplete; do not infer label absence from it. Select only exact existing names allowed by the brief/project. Label strings containing commas cannot be faithfully passed through the CLI's comma-splitting label flag: disclose/omit optional ones before approval, or stop for required ones.
- Recent direct reconciliation: `gh api --method GET repos/OWNER/REPO/issues -f state=all -f sort=created -f direction=desc -f per_page=100 --paginate --slurp`. Unlike search, this uses the issues endpoint directly. `--slurp` produces one outer JSON array of page arrays; validate that shape and every issue record before inspecting pages. This fetches the repository's entire issue/PR history, including pages older than the relevant window, so record that network/time cost; a timeout or resource limit is incomplete reconciliation. Exclude pull-request rows; inspect all relevant records through the attempt's recorded start time (including equal timestamps). Check successful completion and each page's shape. On initial create, inspect the recent window since duplicate search began. Preserve limits and failures in the receipt; incomplete reconciliation never licenses an initial or second create.

## Create and readback

Write the exact approved UTF-8 body using a file API under the project's working-artifact convention; retain it for resume. The path comes from the operation identity, never untrusted title text. Hash a deterministic UTF-8 JSON array `[tracker, project, title, body, labels]` (labels sorted once before approval) with SHA-256; store the algorithm and digest in the receipt. Recompute immediately before mutation and compare to the approved digest.

Invoke `gh issue create --repo OWNER/REPO --title TITLE --body-file BODY_PATH`, adding each existing approved label as a separate `--label LABEL` pair. Every flag and value is a separate argument; TITLE is literal, including quotes, backticks, dollar signs, or leading hyphens. Do not strip or rewrite approved text. Do not add assignees, mentions, projects, attachments, comments, or hidden markers after approval. Label rationale, when useful, belongs in the approved body or local receipt.

Persist `attempted=true` before invocation. Save returned URL/number before any other action and use **get-issue** for readback. Validate the returned URL's host/repository/number against the target. A nonzero exit or timeout can still mean creation succeeded. Record a known identifier even on failure; reconcile it rather than create again. Compare readback title/body and labels with the approved content, reporting discrepancies and verification status honestly. Never use edit/comment/close/reopen to repair them in this skill.

An unknown outcome has no automatic retry. Direct reads and receipt evidence may resolve it to a known created issue; if they do not, report `unknown-outcome` and stop. A later separately authorized attempt requires affirmative evidence that the previous attempt did not create an issue, not just an empty search-index result.
