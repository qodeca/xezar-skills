**2026-09-22 — a latent bug found by the engine team's measurement, fixed in `1b66d2b`.** `local-tree.sh`'s engine allowlist was missing six top-level names, **at every engine version, not because of 0.18.0**: `pi-leader.json`, `automations.json`, `automation-state.json`, `automation-receipts.ndjson`, `automation-log.ndjson`, `automation-poll.lock`. All verified as `join(dataDir, …)` in engine source before adding. Their measured 0.18.0 listing (15 names, boot + after-use) was **already fully covered** — these six hid because they need a feature nobody had enabled (a pi leader attached; an opt-in automations flag). The first project to switch on automations would have found them as a gate failing on every run.

**The general rule, now in that file's header:** *a listing shows what the features you ENABLED write; the source shows what every feature CAN write, and that is the larger set.* Watching engine releases would never have caught these, because nothing was changing.

**Then I applied that rule to my own list and found a WORSE gap (`a39e095`).** A full source enumeration of engine 0.18.0's `dataDir` top level found names **no exact list can ever hold**: atomic writes at `<file>.<pid>.<hex>.tmp` (pid + random hex), `<file>.lock`, and audit rotation `audit.ndjson.1`..`.4`. These need no feature enabled — they exist during normal operation, and `local-tree.sh` runs as a gate **while the engine is live**, so a gate racing an atomic write failed on a file gone a millisecond later. Fixed by matching `<known>` or `<known>.*` (prefix, not exact); `ENGINE_FILES` now holds **base names only**. Stated trade: a stray `runs.json.notes` is skipped — untidiness is cheaper than a false gate failure. Verified 30 names incl. every transient shape pass; stray file and stray dir still fail.

**When this is next revisited, repeat the SOURCE ENUMERATION, not a listing** — and remember some entries are shapes, not names.

**Operational fact worth keeping about engine releases:** `package.json` on engine `main` lags the published version BY DESIGN. The version is stamped during the publish workflow, published, and a bump PR brings the repo in line afterwards. npm can also serve the old version for ~15 minutes after a fully successful publish. So a tag and GitHub Release landing before npm serves the version is **normal, not a failed publish** — do not diagnose it as one.
